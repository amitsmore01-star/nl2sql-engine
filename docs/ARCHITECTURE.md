## 1. Purpose & Principles

### 1.1 What This Engine Does

Converts natural language queries from business users into deterministic, validated SQL `SELECT` statements via a structured JSON intermediate representation. Individual pipeline stages are also exposed as standalone HTTP endpoints so that a Microsoft Fabric agent can orchestrate them independently.

```
User types:  "give me customer name, top acc and sub acc for customer CUST01 in Acme"
Engine returns: SELECT TOP 10000 cd.CustomerName, a_top.AccName, a_sub.AccName
                FROM Major.Customer c
                INNER JOIN ...
                WHERE c.CustomerCID = 'CUST01' AND ...
```

### 1.2 Core Principles

| Principle | What It Means |
|---|---|
| **Zero hardcoding** | No table names, column names, joins, or business rules ever written in code |
| **Schema drives everything** | All behaviour comes from the app schema JSON file |
| **LLM proposes — validator decides** | LLM does language understanding only. Validator has final authority |
| **Deterministic SQL** | SQL is always generated by code — never by an LLM |
| **Modular by design** | Every component is independently testable and replaceable |
| **One function, two callers** | Each pipeline stage is a single internal Python function. Both `/v1/query` and `/v1/tools/{stage}` call the same function — zero duplication |
| **Never assume — always ask** | Any ambiguity → stop and ask. Never proceed on assumption |

### 1.3 What This Document Is

This is the **single source of truth** for the `nl2sql-engine` project. Every architectural decision, every folder name, every coding rule is defined here. If it is not in this document — ask before implementing.

| 36 | Foundry tool input/output contract | Each tool endpoint accepts a `QueryContext` as HTTP request body, runs that one stage, returns updated `QueryContext`. Reason: agent carries state between calls — stateless service, no session needed |
| 37 | Foundry tool stage order | Any order — agent decides which stages to call and in what sequence. Required fields are the agent's responsibility |
| 38 | Foundry tool stage validation | Each tool endpoint validates that required `QueryContext` fields for that stage are present before running. Missing fields → structured `MISSING_CONTEXT_FIELDS` error |
| 39 | One function, two callers | Each stage is implemented as one internal Python function. `/v1/query` calls them in sequence. `/v1/tools/{stage}` calls the same function directly. Zero code duplication |
| 40 | Async model | Everything sync — pipeline stage functions are `def` not `async def`. FastAPI endpoints are `def` not `async def`. LLM providers use `httpx.Client` (sync). Reason: simpler code, easier to test, uvicorn workers provide sufficient concurrency for Phase 1 traffic |
| 41 | Concurrency model | uvicorn runs N worker processes (configured at startup via `--workers N`). Each worker handles one request at a time. Multiple simultaneous requests are served by multiple workers — no async machinery needed in application code |
| 42 | Circuit breaker | None in Phase 1 — retry + timeout is sufficient. Reason: adds complexity for a failure mode that is unlikely in Phase 1 usage. Revisit in Phase 2 if LLM provider instability becomes an issue |
| 43 | Concurrent Foundry tool calls | Behaviour when two tool calls share the same `request_id` concurrently is undefined in Phase 1. Each call is stateless and will succeed independently, but log file entries may interleave. Agent's responsibility to use unique `request_id` per logical request. Full definition deferred to Phase 2 |
| 44 | HTTP client for LLM providers | `httpx` sync client (`httpx.Client`) — not `httpx.AsyncClient`, not `requests`. Reason: consistent library across all providers, built-in timeout support, easy to mock in tests |
| 45 | NL-to-IR abstraction | `NLToIRStrategy` ABC + `NLToIRStrategyFactory`. Concrete strategies live under `src/pipeline/strategies/`. Selected via `llm.nl_to_ir_strategy` in YAML. Phase 1 default: `single_call` |
| 46 | Prompt storage | `config/prompts.yaml` — sectioned (role description, output structure, rules grouped by topic, example sets, examples, user template). Loaded at startup. Assembled by `PromptBuilder` into final prompt strings |
| 47 | Prompt validation | Two-layer — Pydantic validates structure at load; `PromptBuilder.validate()` validates semantics (cross-references, placeholders, required fields per example). Service refuses to start on any validation failure |
| 48 | Pre-LLM intent guard | Single function `run_intent_guard(context)` called from every endpoint accepting `nl_query_original` (`/v1/query`, `/v1/tools/query`, `/v1/tools/nl-to-ir`, `/v1/tools/app-identifier`). Deterministic keyword check (DELETE/DROP/UPDATE/INSERT/TRUNCATE/ALTER/CREATE). Non-select queries return `UNSUPPORTED_INTENT` immediately. No LLM call. Reason: zero-cost protection against non-select queries; never relies on LLM behaviour for safety |
| 49 | Validator source provenance | LLM output includes a `source` field on every table, column, and filter — the exact query phrase that produced that choice. Validator uses these source terms to assign hierarchy roles (e.g. top_acc, sub_acc) by matching against schema hierarchy synonyms. Zero hallucination risk on roles — LLM never produces role values directly |

### 2.2 Design Patterns

These patterns apply across the entire codebase. All new code must follow them.

| Pattern | Where Applied | Why |
|---|---|---|
| **Strategy** | LLM providers, `StageRequirements` per stage in context validator, `NLToIRStrategy` for NL-to-IR transformation | Swap behaviour without changing the caller. Adding a new stage, provider, or NL-to-IR approach = add one class, zero changes elsewhere |
| **Factory** | `LLMProviderFactory`, `ContextValidator._build_registry()`, `NLToIRStrategyFactory` | Centralised object creation — caller never instantiates directly |
| **Repository** | `SchemaRepository` | Abstracts file I/O from business logic — business code never reads files directly |
| **Dependency Injection** | FastAPI `Depends()` for auth; `app.state` for settings and schema repo | No hidden globals, fully testable by swapping dependencies in tests |
| **Template Method** | All pipeline stage functions follow: validate inputs → run logic → log → return context | Every stage has the same shape — predictable, easy to debug |
| **Single Responsibility** | One class, one job — validator validates, builder builds, logger logs | Easier to test, easier to change |
| **Open/Closed** | `StageRequirements` — add new stage by adding new class, never modify existing validator logic | Safe extension without risk of breaking existing stages |


```yaml

  provider: azure_openai
```

**`config/prompts.yaml`** — see Section 4.4 below.

### 4.2 `.env` — Secrets Only

Never in YAML. See Section 2.1 for full list. Note: `FOUNDRY_API_KEY` is a secret and lives in `.env` only.

### 4.3 Merge Order at Startup

```
settings.base.yaml
      +
settings.{ENV}.yaml          ← ENV from .env (dev | prod)
      +
.env                          ← secrets override everything
      =
Final Settings object (Pydantic)
```

`src/config/settings.py` handles this merge. It is the only file that reads from YAML and `.env`. No other file calls `os.getenv()` or reads config directly.

`prompts.yaml` loads independently from the settings stack and is attached as `settings.prompts`. Same single-source rule applies — `settings.py` is the only file that reads from any YAML.

### 4.4 `prompts.yaml` — Prompt Definitions

Separate from service configuration. Holds sectioned prompt definitions used by NL-to-IR strategies. Loaded at startup, validated by Pydantic for structure and by `PromptBuilder.validate()` for semantics.

Structure (top-level keys):

```yaml
nl_to_structured_query:
  role_description:    # what the assistant is
  output_structure:    # exact JSON shape expected
  rules:               # grouped by topic
    output: [...]
    tables: [...]
    columns: [...]
    filters: [...]
    source: [...]
    limit: [...]
    aggregation: [...]
    sort: [...]
  example_sets:        # named groupings of example references
    default: [hierarchy_with_filter, filter_only_date, aggregation_with_limit]
    minimal: [hierarchy_with_filter]
  examples:            # each defined once, referenced by name from sets
    hierarchy_with_filter:
      schema: |
        ...
      query: "..."
      correct: |
        ...
      incorrect: |        # optional, but if present so must why_wrong
        ...
      why_wrong: |
        ...
  user_template:       # must contain <SCHEMA_SUMMARY> and <USER_QUERY> placeholders
```

Active example set selected via `llm.prompt_example_set` in `settings.base.yaml` (default: `default`).

Future strategies (two-call, RAG) may add their own top-level keys here. One file, multiple strategies.

## 5. Schema Model

### 5.1 Schema JSON Structure

Every app has one JSON file in `schemas/{appId}.json`. The filename must match the `appId` field inside the JSON. The engine reads only this file — no hardcoded knowledge.

```json
{
  "appId": "Acme_app",
  "app_name": "Acme",
  "version": "1.0",
  "appSynonyms": ["Acme", "Acme office", "Acme system"],
  "description": "Customer and Account Management",
  "database_type": "SQL Server",
  "tables": [
    {
      "name": "Major.Customer",
      "display_name": "Customer",
      "schema": "Major",
      "synonyms": ["customer", "organization", "org"],
      "versioning": {
        "is_versioned": true,
        "business_key": "CustomerCID",
        "row_key": "CustomerID",
        "effective_date": "VersionEffDate",
```

### 5.3 Junction Tables

Some tables exist purely to link two other tables and are never exposed to users. These are **junction tables**.

**How to mark a junction table in schema JSON:**
```json
{
  "name": "Major.PackagePlan",
  "is_junction_table": true,
  "synonyms": [],
  "description": "Links Major.Package and Major.Plan",
  "columns": [ ... ],
  "relationships": [ ... ]
}
```

**Rules that apply to junction tables:**

| Rule | Detail |
|---|---|
| `is_junction_table: true` | Explicit flag — never inferred |
| `synonyms[]` empty | Valid — not an error for junction tables |
| Never sent to LLM | Excluded from compressed schema summary |
| Never proposed by LLM | LLM only proposes user-facing tables |
| Never matched from NL query | App identifier ignores junction tables |
| Auto-bridged by join resolver | When two tables share a junction bridge — resolver auto-inserts it |
| Generic pattern | Any table with `is_junction_table: true` gets this treatment |

**Example — `Major.PackagePlan`:**
```
User asks for: "packages and their plans"
LLM proposes:  [Major.Package, Major.Plan]
Join resolver: detects no direct link between Package and Plan
               finds Major.PackagePlan bridges them via schema relationships
               auto-inserts Major.PackagePlan + its joins
SQL output:    Package INNER JOIN PackagePlan ON PackageId
               INNER JOIN Plan ON PlanId
```

### 5.4 Schema Validation Rules — Checked at Startup

| Rule | Applies To | Failure Means |
|---|---|---|
| `appId`, `app_name`, `version`, `tables[]` present | All schemas | Missing required field |
| Every table has `name` and `columns[]` | All tables | Incomplete table definition |
| Every non-junction table has `synonyms[]` non-empty | Non-junction only | Missing synonyms |
| Junction tables have `is_junction_table: true` and empty `synonyms[]` | Junction only | Misconfigured junction table |
| Every column has `name` | All columns | Incomplete column definition |
| No duplicate `appId` across files | All apps | Two apps with same ID |
| No duplicate synonym within same app | Non-junction tables | Ambiguous synonym matching |
| Every `relationship.related_table` exists in schema | All tables | Broken relationship |
| No duplicate column names within same table | All tables | Data integrity issue |
| Schema filename must be `{appId}.json` | All schema files | Filename does not match `appId` inside JSON |

**Service refuses to start if any validation fails.**

### 6.2 Each Stage in Plain English

| Stage | Internal Function | Plain English |
|---|---|---|
| **App Identifier** | `run_app_identifier(context)` | Reads the NL query, finds which app schema matches by looking at app name and synonyms. If none found or multiple found — returns clear error immediately |
| **Intent Guard** | `run_intent_guard(context)` | Pure keyword check. Scans NL query for SQL keywords that indicate non-select intent (DELETE, DROP, UPDATE, INSERT, TRUNCATE, ALTER, CREATE). If found, returns `UNSUPPORTED_INTENT` immediately. No LLM call. Cheap deterministic safety gate |
| **NL-to-IR Strategy** | `run_nl_to_ir(context)` | Calls the configured strategy (default `SingleCallStrategy`). Strategy assembles its prompt from the sectioned `prompts.yaml`, sends NL query + schema summary to the LLM in one call, parses the simplified IR (tables, columns, filters, limit, aggregation, sort — each with `source` provenance), populates `context.llm_output`. Other strategies (two-call, RAG) may be plugged in via config without touching this function or the orchestrator |
| **Deterministic Validator** | `run_validator(context)` | Checks every LLM proposal against the actual schema. Rejects anything that doesn't exist. Resolves joins. Auto-applies business rules, versioning conditions. Uses `source` field on duplicate tables to assign hierarchy roles (top_acc, sub_acc) by matching source terms against hierarchy synonyms in the schema |
| **SQL Builder** | `run_sql_builder(context)` | Takes the validated StructuredQuery and generates SQL. Pure code — no LLM involved at all |

> **Intent Guard is invoked by multiple entry points** — the user-facing orchestrator (`/v1/query`) and every Foundry tool endpoint that accepts `nl_query_original` (`/v1/tools/query`, `/v1/tools/nl-to-ir`, `/v1/tools/app-identifier`). The function lives in one file and is called from each entry point. Zero duplication.

### 6.3 QueryContext — Pipeline State Object

`QueryContext` is the single object passed through every stage. Each stage reads from it and adds its outputs to it. It is also the HTTP body for every Foundry tool endpoint.

```python
class QueryContext(BaseModel):
    # Identity
    request_id:           str        # UUID — unique per request
    user_id:              str        # "Phase1_user" in Phase 1
    app_id:               str        # identified app
    app_schema_version:   str        # version field from schema JSON

    # Input
    nl_query_original:    str        # raw NL query — never modified
    nl_query_corrected:   str | None # Phase 2 — spell corrected version

    # LLM output (single field — replaces intent_output and mapping_output)
    llm_output:           dict | None
    # Populated by the NL-to-IR Strategy. Holds the full simplified IR:
    # tables, columns, filters, limit, aggregation, sort.
    # Each table/column/filter includes a "source" field tracing back to the query.

    # Validator outputs
    resolved_tables:  list      # validated table dicts from llm_output.tables ,each: {"table": "Major.Customer", "source": "customer"}
    resolved_columns: list      # validated column dicts from llm_output.columns,each: {"table": "...", "column": "...", "source": "..."}
    resolved_filters: list      # validated filter dicts from llm_output.filters,each: {"table": "...", "column": "...","operator": "...", "value": "...","source": "..."}
    resolved_joins:       list      # join graph result
    applied_rules:        list      # business rules injected

    # Final outputs
    structured_query:     StructuredQuery | None
    sql:                  str | None

    # Observability
    latency_ms:           dict      # per stage timing
    total_latency_ms:     int       # end-to-end
    token_usage:          dict      # step1, step2, total
    warnings:             list      # non-fatal issues

    # Outcome
    status:               str       # success | failed | cancelled
    error:                dict | None
```

> `intent_output` and `mapping_output` fields have been removed (architecture v1.6). The single `llm_output` field replaces both. If the agent sends a `QueryContext` with the old field names, Pydantic rejects with `422 Unprocessable Entity`.

### 6.4 Required Fields Per Stage

Each Foundry tool endpoint validates these fields are present and non-null before running. Missing fields → `MISSING_CONTEXT_FIELDS` error returned immediately.

| Stage | Required fields in QueryContext before calling |
|---|---|
| **App Identifier** | `nl_query_original` |
| **Intent Guard** | `nl_query_original` |
| **NL-to-IR Strategy** | `nl_query_original`, `app_id`, `app_schema_version` |
| **Deterministic Validator** | `app_id`, `app_schema_version`, `llm_output` |
| **SQL Builder** | `app_id`, `structured_query` |
| **Full pipeline (tools/query)** | `nl_query_original` |

> **`request_id` is excluded from all validation checks** — `QueryContext.request_id` has `default_factory=lambda: str(uuid.uuid4())`. Pydantic auto-generates it if the agent does not provide one. It is always guaranteed to be present by the time the context validator runs.

> **`app_id` flow in tool scenario** — The agent sends `app_id=""` to app-identifier and intent-guard (both accept empty `app_id`). The app-identifier stage reads `nl_query_original`, identifies the app, and writes `app_id="Acme_app"` into the returned context. The agent then carries that populated context into the next stage call. `app_id` and `app_schema_version` are typed as `str` with default `""` on `QueryContext` — they are NOT `Optional`. Pydantic rejects `None` for these fields. The empty string `""` is the correct "not yet populated" state.

> **`llm_output` flow** — populated by NL-to-IR Strategy stage. Validator requires it present and non-null. Agent may also hand-craft a `llm_output` payload and call the validator directly, bypassing the strategy entirely — this is supported and tested.

**Why this design:** The agent is free to call any stage in any order. The validation layer is what enforces correctness — the engine does not assume any call order. If the agent skips the NL-to-IR Strategy and calls the validator directly with a hand-crafted `llm_output`, that is valid as long as `llm_output` is present and correctly structured.

## 7. LLM Layer

### 7.1 Provider Abstraction

All providers implement the same `LLMProvider` ABC. Switch provider by changing `LLM_PROVIDER` in `.env` — zero code change.

All providers are **synchronous**. No `async def` anywhere in the LLM layer. uvicorn worker processes handle request concurrency — the application code does not need to.

```python
# src/llm/base.py
class LLMProvider(ABC):
    @abstractmethod
    def complete(
        self,
        system_prompt: str,
        user_prompt: str
    ) -> str:
        """Call LLM and return text response. Sync — blocking call."""
        ...

    @abstractmethod
    def provider_name(self) -> str:
        """Return provider identifier string."""
        ...
```

### 7.2 All Four Providers

| Provider | Class | Config Value | Used For |
|---|---|---|---|
| Mock | `MockLLMProvider` | `mock` | All tests — zero API calls, returns instantly |
| OpenAI | `OpenAIProvider` | `openai` | GPT-4o-mini (Phase 1 default) |
| Azure OpenAI | `AzureOpenAIProvider` | `azure_openai` | Production-ready alternative |
| Anthropic | `AnthropicProvider` | `anthropic` | Claude Sonnet latest |

**Factory pattern:**
```python
# src/llm/factory.py
class LLMProviderFactory:
    @staticmethod
    def create(settings: Settings) -> LLMProvider:
        providers = {
            "mock":         MockLLMProvider,
            "openai":       OpenAIProvider,
```

**HTTP client — all real providers use `httpx.Client` (sync):**
```python
# Pattern used in every real provider
import httpx
import time

class OpenAIProvider(LLMProvider):
    def complete(self, system_prompt: str, user_prompt: str) -> str:
        with httpx.Client(timeout=self.settings.llm.timeout_seconds) as client:
            response = client.post(
                url="https://api.openai.com/v1/chat/completions",
                headers={"Authorization": f"Bearer {self.settings.openai_api_key}"},
                json={...}
            )
            response.raise_for_status()
            return response.json()["choices"][0]["message"]["content"]
```

**Retry + timeout — all real providers, sync retry loop:**
```python
def complete(self, system_prompt: str, user_prompt: str) -> str:
    last_error = None
    for attempt in range(self.settings.llm.retry_max):
        try:
            return self._call(system_prompt, user_prompt)
        except (httpx.TimeoutException, httpx.HTTPStatusError) as e:
            last_error = e
            if attempt < self.settings.llm.retry_max - 1:
                wait = self.settings.llm.retry_backoff_seconds ** attempt
                time.sleep(wait)
    raise LLMOutputParseError(f"LLM call failed after {self.settings.llm.retry_max} attempts: {last_error}")
```

- Retry up to `llm.retry_max` times (from YAML)
- Exponential backoff: `llm.retry_backoff_seconds ^ attempt` seconds between retries (from YAML)
- Hard timeout per call: `llm.timeout_seconds` (from YAML)
- No circuit breaker in Phase 1 — retry + timeout is sufficient
- MockLLMProvider: no retry, no HTTP — returns canned response instantly

### 7.3 NL-to-IR Strategy

The "how we use the LLM" question is decoupled from "which LLM" via a second Strategy layer:

```python
# src/pipeline/strategies/base.py
class NLToIRStrategy(ABC):
    """
    Abstract strategy for converting NL query to structured IR.
    Implementations decide:
      - How many LLM calls to make
      - What prompts to use
      - What IR shape to produce
      - How to parse LLM output
    All implementations write the final IR to context.llm_output.
    """
    @abstractmethod
    def execute(self, context: QueryContext, schema_summary: str) -> QueryContext:
        ...
    @abstractmethod
    def strategy_name(self) -> str:
        ...
```

**Available strategies:**

| Strategy | Class | Config Value | Status |
|---|---|---|---|
| Single Call | `SingleCallStrategy` | `single_call` | Phase 1 default |
| Agentic | `AgenticStrategy` | `agentic` | Phase 2 — reserved |
| RAG | `RAGStrategy` | `rag` | Phase 2 — reserved |

Switch via `llm.nl_to_ir_strategy` in YAML. Adding a new strategy is one new class + one factory registry entry. Zero changes elsewhere — orchestrator, validator, SQL builder, and tool endpoints all keep working unchanged.

**Factory pattern:**

```python
# src/pipeline/strategies/factory.py
class NLToIRStrategyFactory:
    @staticmethod
    def create(settings: Settings, llm_provider: LLMProvider, logger: StructuredLogger) -> NLToIRStrategy:
        strategies = {
            "single_call": SingleCallStrategy,
            # "agentic": AgenticStrategy,     # Phase 2
            # "rag": RAGStrategy,             # Phase 2
        }
        cls = strategies.get(settings.llm.nl_to_ir_strategy)
        if not cls:
            raise UnknownStrategyError(settings.llm.nl_to_ir_strategy)
        return cls(settings, llm_provider, logger)
```

### 7.4 SingleCallStrategy — Simplified IR

**Why single call:** With a deterministic validator handling business rules, joins, hierarchy, and business-key resolution, the LLM's job reduces to identifying which tables, columns, and filters the user is asking about. Modern LLMs do this reliably in one call when given a clean schema summary and a clear prompt. One call halves latency and cost vs two calls.

**Why simplified IR:** The IR mirrors SQL clause structure — tables, columns, filters, limit, aggregation, sort. The validator handles complex transformations; the LLM produces only what the SQL builder needs to know. This is the standard industry pattern for Approach 2 (LLM proposes IR, code builds SQL).

**Output IR shape:**

```json
{
  "tables": [
    {"table": "Major.Customer", "source": "customer"}
  ],
  "columns": [
    {"table": "Major.CustomerDemographics", "column": "CustomerName", "source": "customer name"}
  ],
  "filters": [
    {
      "table": "Major.Customer",
      "column": "CustomerCID",
      "operator": "=",
      "value": "CUST01",
      "source": "customer CUST01"
    }
  ],
  "limit": null,
  "aggregation": {
    "type": "COUNT",
    "group_by": [{"table": "Major.Customer", "column": "CustomerCID"}]
  },
  "sort": [
    {"table": "Major.Acc", "column": "AccID", "direction": "DESC"}
  ]
}
```

**Key field: `source`** — every table, column, and filter carries a `source` field. The LLM must copy the exact word or phrase from the user query that led to that choice. This serves the validator for:
- Hierarchy role assignment (matches `source` against schema hierarchy synonyms)
- Self-join detection (same table twice with different sources)
- Audit trail (full traceability from query word to SQL clause)
- Warning generation (source far from schema synonym → flag warning)

**Phase 1 scope of IR fields:**

| Field | Phase 1 behaviour |
|---|---|
| `tables`, `columns`, `filters` | Fully validated and used by SQL builder |
| `limit` | Captured and applied by SQL builder |
| `aggregation` | **Captured but not executed in Phase 1.** Validator records it. SQL builder ignores it. Phase 2 enables aggregation in SQL output |
| `sort` | **Captured but not executed in Phase 1.** Same deferral as aggregation |

### 7.5 prompts.yaml — Sectioned Prompt File

Prompts are not hardcoded. They live in `config/prompts.yaml` in sectioned form — role description, output structure, rules grouped by topic, example sets, examples, user template. The `PromptBuilder` class assembles these sections into the final prompt string at startup.

**Top-level structure (Phase 1):**

```yaml
nl_to_structured_query:
  role_description: |
    ...
  output_structure: |
    ...
  rules:
    output:      [...]
    tables:      [...]
    columns:     [...]
    filters:     [...]
    source:      [...]
    limit:       [...]
    aggregation: [...]
    sort:        [...]
  example_sets:
    default: [hierarchy_with_filter, filter_only_date, aggregation_with_limit]
    minimal: [hierarchy_with_filter]
  examples:
    hierarchy_with_filter:
      schema:    |
        ...
      query:     "..."
      correct:   |
        ...
      incorrect: |
        ...
      why_wrong: |
        ...
    filter_only_date:
      ...
    aggregation_with_limit:
      ...
  user_template: |
    Schema summary:
    <SCHEMA_SUMMARY>
    User query:
    <USER_QUERY>
```

**Assembly order (fixed):**

```
role_description
↓
output_structure
↓
STRICT RULES
  output → tables → columns → filters → source → limit → aggregation → sort
↓
EXAMPLES
  each example: schema → query → correct → incorrect → why_wrong
```

**Active example set** — selected via `llm.prompt_example_set` in `settings.base.yaml`. Phase 1 default: `default`.

**Validation — two layers:**

| Layer | Tool | What it catches |
|---|---|---|
| Structural | Pydantic models in `src/config/prompts_models.py` | Missing top-level keys, wrong types, malformed YAML |
| Semantic | `PromptBuilder.validate()` | Broken example references, missing required fields per example, `incorrect` without `why_wrong` (or vice versa), `user_template` missing placeholders, configured example set not found |

If either layer fails, the service refuses to start with a clear error.

**`PromptBuilder` interface:**

```python
class PromptBuilder:
    @staticmethod
    def validate(spec: PromptSpec) -> None: ...
    @staticmethod
    def build_system_prompt(spec: PromptSpec, example_set_name: str) -> str: ...
    @staticmethod
    def render_user_prompt(spec: PromptSpec, schema_summary: str, user_query: str) -> str: ...
```

Strategies call `build_system_prompt` once at construction (system prompt is identical across requests) and `render_user_prompt` per request (only schema summary and user query change).

**Future strategies** add their own top-level keys to `prompts.yaml` (e.g. `nl_to_intent`, `nl_to_mapping` for two-call). Same file, multiple top-level keys, one per strategy.

### 7.6 What LLM Never Does

| Never | Why |
|---|---|
| Generates SQL | SQL is always deterministic code |
| Decides if a query is select or non-select | Pre-LLM Intent Guard handles this deterministically |
| Assigns hierarchy roles (top_acc, sub_acc) | Validator derives from `source` field + schema synonyms |
| Corrects spelling | Phase 2 — Levenshtein only |
| Has final authority | Validator decides — LLM proposes |
| Sees full schema JSON | Compressed summary only |
| Sees junction tables | Excluded from summary — join resolver handles bridging |
| Sees conversation history | Single-turn in Phase 1 |

### 7.7 Token Budget

| Item | Target | Hard Limit |
|---|---|---|
| System prompt (built once at startup) | ~1,500 tokens | 2,000 |
| User prompt (per request) | ~300-500 tokens | 800 |
| LLM response (simplified IR JSON) | ~400-600 tokens | 1,000 |
| **Total per query** | **~2,200-3,100 tokens** | **3,800** |

The system prompt is the largest component because it carries rules and few-shot examples. It is sent once per request but reused across all requests within a process — strategies build it once at construction.

## 8. Deterministic Validator

### 8.1 What It Validates

Every LLM proposal is checked against the actual schema. If it does not exist in the schema — it is rejected. No exceptions.

| Validation | Check | Error if Fails |
|---|---|---|
| Tables | Every proposed table exists in schema | `NO_RELEVANT_TABLES` |
| Columns | Every proposed column belongs to its table | `NO_RELEVANT_COLUMNS` |
| Join path | A join path exists between all required tables | `NO_JOIN_PATH` |

> Intent validation is handled upstream by the deterministic Intent Guard (Section 6.2) before any LLM call. Non-select queries return `UNSUPPORTED_INTENT` and never reach the validator.

### 8.2 Join Resolution — Acme Example

| From | Column | To | Column |
|---|---|---|---|
| `Major.Customer` | `CustomerID` | `Major.CustomerDemographics` | `CustomerID` |
| `Major.Customer` | `CustomerID` | `Major.Acc` | `CustomerID` |
| `Major.Acc (a_top)` | `AccID` | `Major.Acc (a_sub)` | `ParentAccID` |

### 8.3 Junction Table Auto-Bridging

When the join resolver finds two resolved tables that have **no direct relationship** in the schema, it checks whether a junction table bridges them.

**Algorithm:**
```
For each pair of resolved tables with no direct join:
    Search all junction tables (is_junction_table: true)
    Find one whose relationships link both tables
    Auto-insert junction table + both joins
    Log: "Junction bridge auto-inserted: Major.PackagePlan"
```

**Example — Package + Plan:**
```
Resolved tables: [Major.Package, Major.Plan]
Direct join:     None exists
Junction check:  Major.PackagePlan links Package (PackageId) + Plan (PlanId) ✅
Auto-inserted:   Major.Package
                 INNER JOIN Major.PackagePlan ON Major.Package.PackageId = Major.PackagePlan.PackageId
                 INNER JOIN Major.Plan ON Major.PackagePlan.PlanId = Major.Plan.PlanId
```

User never sees `PackagePlan`. LLM never knew it existed. Join resolver handled it entirely from schema relationships.

### 8.4 Business Rules — Auto Applied

Applied automatically from schema `business_rules.active_record`. Never hardcoded in code.

**`Major.Customer`:**
```sql
VersionTermDate IS NULL
AND ISNULL(DeletedFlag, 0) = 0
AND VoidedDate IS NULL
```

**`Major.Acc`:**
```sql
TermDate IS NULL
```

**Filter control — suppress tokens:**
If NL query contains: `history`, `historical`, `all versions` → business rules suppressed for that table.

### 8.5 Versioning Rules — Auto Applied

For tables where `is_versioned: true` — active condition auto-applied:

**`Major.Customer`:** `VersionTermDate IS NULL`
**`Major.Package`:** `VersionTermDate IS NULL`

### 8.6 Hierarchy Rules — Source-Driven Role Assignment

The validator does not rely on the LLM to assign hierarchy roles. Role assignment is fully deterministic, driven by the `source` field on each table entry in `llm_output`.

**Algorithm:**

```
For each entry in llm_output.tables:
  If table appears more than once in llm_output.tables:
    For each instance, take its "source" string
    Match source against hierarchy synonyms in schema (case-insensitive, whole-word)
    Assign role based on which hierarchy bucket the source matched
    If source matches no hierarchy synonym, role = None (warning logged)
```

**Example — for `Major.Acc` with hierarchy config in schema:**

```json
"hierarchy": {
  "top_Acc": {
    "synonyms": ["top", "top acc", "top level", "parent acc"],
    "condition": "AccLevelConfig = 0",
    "parent_condition": "ParentAccID IS NULL"
  },
  "sub_Acc": {
    "synonyms": ["sub", "sub acc", "child", "subsidiary"],
    "condition": "AccLevelConfig = 1",
    "parent_condition": "ParentAccID IS NOT NULL"
  }
}
```

If `llm_output.tables` contains:
```json
[
  {"table": "Major.Acc", "source": "top acc"},
  {"table": "Major.Acc", "source": "sub acc"}
]
```

Validator assigns:
- First instance → role `top_acc` → alias `a_top` → conditions `AccLevelConfig = 0 AND ParentAccID IS NULL`
- Second instance → role `sub_acc` → alias `a_sub` → conditions `AccLevelConfig = 1 AND ParentAccID IS NOT NULL`

Self-join: `a_top.AccID = a_sub.ParentAccID`

**Zero hallucination risk** — the LLM never produces a role value. It only provides the `source` term it copied from the query. The validator deterministically maps source → role via schema synonyms.

## 9. SQL Builder

### 9.1 How It Works

Takes a validated `StructuredQuery` object and generates SQL. Pure Python — no LLM, no schema lookups, no business logic. Just assembles the SQL from what the validator already confirmed.

```
StructuredQuery → SelectBuilder → JoinBuilder → WhereBuilder → SQLBuilder → SQL string
```

### 9.2 Safety Guards

| Guard | Rule |
|---|---|
| `TOP` limit | Always appends `TOP {DEFAULT_TOP_ROWS}` (default 10,000) |
| Parameterized values | Filter values always bound as parameters — never string-interpolated |
| No LLM import | `sql_builder.py` must never import from `src/llm/` |

### 9.3 Golden Example — Input → Output

**Input NL query:**
```
"give me customer name, top acc and sub acc for customer CUST01 in Acme"
```

**Expected SQL output:**
```sql
SELECT TOP 10000
  cd.CustomerName  AS CustomerName,
  a_top.AccName    AS TopAccName,
  a_sub.AccName    AS SubAccName
FROM Major.Customer c
INNER JOIN Major.CustomerDemographics cd
  ON c.CustomerID = cd.CustomerID
INNER JOIN Major.Acc a_top
  ON c.CustomerID = a_top.CustomerID
INNER JOIN Major.Acc a_sub
  ON a_top.AccID = a_sub.ParentAccID
WHERE
  c.CustomerCID              = 'CUST01'
  AND c.VersionTermDate      IS NULL
  AND ISNULL(c.DeletedFlag, 0) = 0
  AND c.VoidedDate           IS NULL
  AND a_top.AccLevelConfig   = 0
  AND a_top.ParentAccID      IS NULL
  AND a_sub.AccLevelConfig   = 1
  AND a_sub.ParentAccID      IS NOT NULL;
```

**This exact output is the golden test in `tests/test_e2e.py`. If this test fails — nothing else proceeds.**


- `tools/tool_auth.py` → `require_foundry_key()` — reads `FOUNDRY_API_KEY` from settings

## 11. Logging

### 11.1 Log Stages and Payloads

Every stage emits a structured JSON log entry. All entries include `request_id`, `user_id`, `app_id`, `stage`, `timestamp_utc`, `latency_ms`. This applies equally whether the stage is called via `/v1/query` or `/v1/tools/{stage}` — the same internal function logs the same way.

| Stage Constant | When Emitted | Key Payload Fields |
|---|---|---|
| `REQUEST_RECEIVED` | Request arrives | `nl_query_original`, `app_id`, `caller` (user \| foundry) |
| `APP_DETECTED` | App identified | `app_id`, `schema_version`, `match_method` |
| `INTENT_GUARD_RESULT` | Intent guard runs | `passed` (bool), `keywords_detected` (list if blocked) |
| `LLM_OUTPUT` | NL-to-IR Strategy complete | `strategy_name`, `llm_output` (the full simplified IR), `token_usage`, `latency_ms` |
| `VALIDATION_RESULT` | Validation complete | `resolved_tables`, `resolved_columns`, `resolved_joins`, `applied_rules`, `assigned_roles` |
| `STRUCTURED_QUERY_BUILT` | StructuredQuery ready | Full structured query JSON |
| `SQL_BUILT` | SQL generated | Full SQL string |
| `RESPONSE_SENT` | Response returned | `status`, `total_latency_ms`, `total_tokens_used` |
| `USER_FEEDBACK` | Feedback received | `status`, `expected_output`, `actual_sql` |

**Total log stages: 9** (unchanged count — `INTENT_GUARD_RESULT` and `LLM_OUTPUT` replace the previous `LLM_INTENT_OUTPUT` + `LLM_SCHEMA_MAPPING_OUTPUT` pair).

### 11.4 Rotation Behaviour

Log rotation is triggered on write. Before each log entry is written, the logger checks whether the current file's date matches today. If the date has changed, the existing file is moved to `{log_archive_dir}/YYYY-MM-DD/` and a new file is started. This ensures correct rotation even when the service runs continuously without a restart.

## 12. Error Handling

### 12.1 All Error Codes

Defined in `src/core/constants.py`:

| Error Code | When | HTTP Status |
|---|---|---|
| `APP_NOT_DETERMINED` | No app matched in NL query | 200 (business error) |
| `MULTIPLE_APPS_MATCHED` | NL query matched 2+ apps | 200 (business error) |
| `NO_RELEVANT_TABLES` | LLM proposed tables not in schema | 200 (business error) |
| `NO_RELEVANT_COLUMNS` | LLM proposed columns not in table | 200 (business error) |
| `NO_JOIN_PATH` | No join path between required tables | 200 (business error) |
| `UNSUPPORTED_INTENT` | Intent Guard detects non-select keyword in query (deterministic pre-LLM check) | 200 (business error) |
| `VALIDATION_FAILED` | Validator rejected LLM proposals | 200 (business error) |
| `LLM_OUTPUT_PARSE_ERROR` | LLM returned malformed JSON | 200 (business error) |
| `MISSING_CONTEXT_FIELDS` | Required QueryContext fields missing in tool endpoint request | 400 |
| `UNAUTHORIZED` | Missing or wrong API key (either key) | 401 |
| `SCHEMA_LOAD_ERROR` | Schema file missing, invalid, or filename does not match appId | 503 |
| `UNKNOWN_STRATEGY` | `nl_to_ir_strategy` value in settings does not match any registered strategy | 503 |
| `INTERNAL_ERROR` | Unhandled exception | 500 |

**`MISSING_CONTEXT_FIELDS`:** Returned only by Foundry tool endpoints when the agent's `QueryContext` body is missing a required field for that stage. Returns HTTP 400 (bad request) because the error is in what the agent sent, not in the pipeline logic. The response body lists exactly which fields are missing so the agent can fix its call.

**`UNKNOWN_STRATEGY`:** Raised at startup if `llm.nl_to_ir_strategy` value does not match any registered strategy in `NLToIRStrategyFactory`. Service refuses to start. HTTP 503 used if encountered after startup (e.g. via misconfigured runtime swap).

### 12.2 Error Flow

```
Exception raised anywhere in pipeline
        │
        ▼
Caught by stage's own try/except
        │
        ▼
QueryContext.error populated
QueryContext.status = "failed"
        │
        ▼
Logged with full detail
        │
        ▼
Structured error response returned
No raw stack traces to client — full detail in log only
```

## Authentication

### Overview
All endpoints except /health and /ready require API key authentication.
Authentication is enforced via FastAPI dependencies declared on each route.

### Keys
| Key Name         | Env Variable      | Protects              |
|------------------|-------------------|-----------------------|
| Client API Key   | CLIENT_API_KEY    | POST /v1/query        |
| Foundry API Key  | FOUNDRY_API_KEY   | POST /v1/tools/*      |

### Header
Both keys are passed by the caller in the same header:
```  
    X-API-Key: <key value>
```
The route being called determines which key is validated against.

### Key Storage
- Keys are stored in .env only — never in YAML files
- settings.py reads both keys via os.getenv()
- YAML files hold no key values

### Environment Behaviour
- prod: missing key at startup raises ValueError — service will not start
- dev: missing key allowed — every request to that route returns 401

### Auth Failure Response
Both missing and incorrect keys return the same response (no info leakage):
  HTTP 401
  { "detail": "Unauthorized" }

### Exempt Routes
- GET /health
- GET /ready

### Implementation
- src/api/auth.py contains two dependency functions:
    require_client_key  → validates X-API-Key against CLIENT_API_KEY
    require_foundry_key → validates X-API-Key against FOUNDRY_API_KEY
- Each protected route declares its dependency:
    POST /v1/query           → Depends(require_client_key)
    POST /v1/tools/*         → Depends(require_foundry_key)
- Auth logic: if header missing, empty, or does not exactly match
  the configured key → return 401. No whitespace trimming — exact match only.
